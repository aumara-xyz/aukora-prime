## Runtime evidence

These are dated headline claims, quoted from the plan or pilot runbook. Every claim without stranger-checkable evidence is **REPORTED**. No current deployment observation is inferred. A missing commit is explicit, not guessed. The public table does not cache a PASS: executable pointers remain UNPERFORMED until the audit checks them.

```sh
node scripts/audit/runtime-claims.mjs --write
node scripts/audit/runtime-claims.mjs --check
node scripts/audit/runtime-claims.mjs --check --offline
```

The JSON has a closed `aukora-runtime-claims/v1` schema (at most twelve rows). `verification` is `reported` with `evidence: "reported-only"`, or `verified` with an evidence pointer. A claimed verified row that cannot be checked fails the audit, including offline CI rows. `--write` renders and audits pointers; generated prose grants no verification by itself. `--check` also refuses stale generated bytes. All evidence work shares a 25-second budget; each child or request has at most five seconds. No harness archive or build is needed for this audit.

Pointers use `kind: "clone"` with an argv array (`node`, `python3`, `bash` or `sh`, then a repository script), `timeoutMs` up to 5000 and the exact stdout `stdoutSha256`; the clone must be clean, and the audit prints its actual checked HEAD. The row's commit identifies the dated reported runtime; reproduction at today's checkout does not attest that historical run. `kind: "ci"` carries `runId`, `attempt`, exact `job` and `artifact`: the unauthenticated [public API](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run-attempt) must bind the run and successful job to the commit and retain a nonexpired artifact. This checks public metadata, not artifact contents or raw check counts; downloading GitHub artifacts may require sign-in. API unavailability is UNPERFORMED, never VERIFIED. `kind: "ledger"` carries an `evidence/` export `file` and `sha256`, a separately retained `publicKey` and `keySha256`, optional `anchor` (or null), `approval` (an exact canonical release approval file, or null for a generic prefix), `sequence` and `entryHash`; the existing cold verifier checks the exact prefix and selected entry. When supplied, approval bytes must be committed, match that signed apply entry and name the row's release commit. Without them, verification covers a signed prefix only. Digests identify supplied bytes; they do not independently attest the key or the events.

Operator step (not executed by this audit): run **on the node**, with the record of the separately identified running release:

```sh
scripts/audit/export-pilot-evidence.sh --db FILE --public-key PUBLIC.pem \
  --record genesis-artifacts.json --approval approval.json --approval-seq N \
  --launch launch-url.json --out NEW_DIRECTORY
```

It produces `ledger-export.json`, `gate-public.pem`, `release-approval.json`, `release-digest.json`, `ui-probe.json` and `verification.txt`, with a signed prefix through that approval, its exact public approval bytes, release record digest, allowlisted ui-probe result and offline verification output. Collection takes at most twenty seconds and the UI child at most five. It never reads a private signing key. Directories are 0700 and files 0600 even under umask 002. Review these files before committing them under `evidence/` and updating the matching JSON row. Unknown or private signed fields refuse the entire prefix instead of being redacted; the historical pilot ledger may therefore be unexportable through this public profile and stays REPORTED. Supporting that history needs a reviewed public-safe proof format, not weaker filtering. Keep the public key and ledger head separately from the producer. The documented head publisher is on branch `ledger-anchor`, `anchors/gate-ledger.jsonl`; an owner-controlled publisher is not an independent witness.

A signed ledger proves the covered signature and chain relations, not human identity, attendance, process-loaded bytes, browser rendering, memory quality, containment or latestness. UI HTTP responses do not prove a rendered screen. Probe-only releases and stand-in staging keys do not qualify the live pilot. Each row names the additional evidence its particular statement needs.
